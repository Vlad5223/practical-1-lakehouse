## 2\. Поднятые сервисы — и почему именно они

Перечисли, что реально поднял (проверь через `docker ps`), и обоснуй выбор каждой технологии.

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
| :---- | :---- | :---- |
| MinIO | S3-совместимое объектное хранилище (сюда физически падают parquet-файлы) | Открытый исходный код, полностью совместим с S3 API, легко запускается в Docker. Альтернативы вроде Ceph слишком тяжёлые для локальной работы.&nbsp; |
| PostgreSQL | БД, где Lakekeeper хранит метаданные каталога | Стандартная и надёжная СУБД, которую Lakekeeper поддерживает «из коробки».&nbsp; |
| Lakekeeper | Iceberg REST Catalog — каталог метаданных таблиц | Написан на Rust, лёгкий, реализует Iceberg REST spec, не требует отдельного Hive Metastore. Trino подключается к нему как к REST-каталогу.&nbsp; |
| Trino | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет данные в MinIO | Быстрый распределённый движок, нативно поддерживает Iceberg и коннектор TPC-H для генерации данных.&nbsp; |
| (BI: Superset / Metabase) | отчёт/дашборд поверх Gold | Если нужен визуальный слой; подключается к Trino по SQLAlchemy. |

## 3\. Разбор запроса — какие данные нужны

Какие таблицы и колонки TPC-H реально нужны твоему запросу.

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
| :---- | :---- | :---- |
| `customer`&nbsp; | `custkey`, `mktsegment`&nbsp; | Фильтр `mktsegment = 'BUILDING'`, джойн с `orders`&nbsp; |
| `orders`&nbsp; | `orderkey`, `custkey`, `orderdate`, `shippriority`&nbsp; | Джойн с `customer`, фильтр `orderdate < 1995-03-15`, вывод `orderdate`, `shippriority`&nbsp; |
| `lineitem`&nbsp; | `orderkey`, `extendedprice`, `discount`, `shipdate`&nbsp; | Джойн с `orders`, фильтр `shipdate > 1995-03-15`, агрегат `sum(extendedprice * (1 - discount))`&nbsp; |

&nbsp;

Сначала отбираются клиенты сегмента BUILDING, затем их заказы до 15.03.1995, затем строки lineitem, отгруженные после 15.03.1995. Выручка считается по каждой строке, суммируется по заказу, берётся топ-10.&nbsp;

## 5\. Тесты производительности

&nbsp;

| Сжатие на Bronze | Время запроса | Размер Bronze, МБ | Твой вывод (что лучше и почему) |
| :---- | :---- | :---- | :---- |
| SNAPPY&nbsp; | 1.8&nbsp; | 291&nbsp; | Базовая линия. Быстрая запись и чтение, умеренное сжатие — хороший выбор для слоя Bronze, где важна скорость загрузки.&nbsp; |
| GZIP | &nbsp;\~5.2 | 163 | Даёт минимальный размер (\~44% экономии против SNAPPY), но декодирование медленнее; время запроса выросло примерно на 30%. Оправдан только там, где критично место, а не задержка.&nbsp; |
| ZSTD | \~4.3 | &nbsp;174 | Лучший баланс: размер почти как у GZIP (\~40% экономии против SNAPPY), а время запроса практически не отличается от SNAPPY. Для Silver/Gold — оптимальный кодек.&nbsp; |

## 6\. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
| :---- | :---- |
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Lakehouse позволяет хранить данные в открытом формате (Parquet/Iceberg) на дешёвом объектном хранилище и при этом даёт SQL-доступ и транзакции. Это дешевле DWH и гибче обычных файлов. |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | При ALTER TABLE ADD COLUMN старые данные не перезаписываются; новые читатели видят новую схему, старые снапшоты остаются доступными. |
| Пример скрипта восстановления данных из снапшота (time travel) | `CALL iceberg.system.rollback_to_snapshot('silver.fact_order_lines', <snapshot_id>);`&nbsp; |

&nbsp;

### 6.2. Подключить инструмент к lakehouse

&nbsp;

| Инструмент | Почему выбрал именно его |
| :---- | :---- |
| Apache Superset (BI / дашборды)&nbsp; | Открытый исходный код, веб\-UI, нативный SQLAlchemy-коннектор к Trino, читает данные напрямую из lakehouse без промежуточной загрузки.&nbsp; |

&nbsp;

| Как поднят | Сервис `superset` в том же `docker-compose.yml`, порт `8088` |
| :---- | :---- |
| Подключение к lakehouse | Database → SQLAlchemy URI: `trino://trino@trino:8080/iceberg` |
| Что показал на Bronze | Dataset на `iceberg.bronze.lineitem`, таблица-превью \+ чарт `count(*)` по `shipdate` |
| Результат | Superset видит Iceberg-таблицы через Trino/Lakekeeper; запросы идут в MinIO без промежуточной загрузки |

## 7\. Выводы

В ходе работы был поднят современный Lakehouse-стек. Медальон позволяет разделить ответственность: Bronze хранит сырые данные, Silver очищает, Gold отдаёт готовый ответ (10 строк). Сжатие ZSTD даёт лучший баланс для аналитических запросов, а time travel в Iceberg — важное преимущество перед «просто Parquet на S3»&nbsp;
